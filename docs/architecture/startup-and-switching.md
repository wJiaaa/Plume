# 启动、打开大会话、切换会话：实测与约定

三条路径各量了一遍：冷启动到首帧、打开一个几百条消息带子代理的历史会话、在几个会话之间来回切。
本文记的是量到的数、找到的根因、改了什么，以及看到了但不改的那几项。

量法：从本机会话库拷一份（`sqlite3 .backup`，不拷 `settings.json`），配一个指向不存在地址的假模型和
5 台 stdio 假 MCP 服务器（`e2e/mcp-defer-server.ts`）。主进程开 `--inspect`，把 `ipcMain` 里已注册的
handler 包一层记时间、`v8.serialize` 记载荷；每 5ms 一次定时器量主进程事件循环最长卡多久；渲染进程
记 longtask 和点下去到画出来。三个样本会话：284 条消息 / 5.3MB（其中子代理记录 3.9MB）、535 条 /
4.8MB、696 条 / 3.1MB。

## 约定：点开一个会话只是读，不拉起 agent

`sessions:transcript` 只读日志，不起 `AgentSession`——起一个要加载技能、插件，连上每一台 MCP 服务器。
这条约定写在四处注释里，但实际被绕过了：输入框旁的上下文表一挂上就调 `sessions:contextBreakdown`，
而那个 handler 会 `ensureLiveSession`。于是每点开一个历史会话，整套 agent 都被拉起来。

| 打开历史会话（5 台 MCP） | 改前 | 改后 |
| --- | --- | --- |
| 新起子进程 | 5 个（配 30 台就是 30 个，主进程卡 65ms） | 0 |
| 之后每次切回的 `sessions:capabilities` | 327KB（技能全文） | 0KB |

现在没在跑的会话从日志回答（`storedContextBreakdown`、`storedSubAgents`）：

- **上下文读数**：日志里 `context` 记录存着上一次真正发出去的 system prompt 和工具表，活着的会话量的
  也正是这一份（`describeRecordedContext` 两边共用），所以读数一致，发一句话之后表不会跳。日志答不了
  的——从没发过请求、侧边聊天——照旧拉起会话。
- **子代理名单与记录**：原先名单只在会话被拉起时才回到面板上，面板靠的正是上面那次误拉起。现在
  `readSubAgents` 从日志读，`AgentSession` 打开时和没在跑时共用同一个函数、同一个登记簿，`list` /
  `detail` 的形状（含 `resumable`）一样。和子代理说话、把它移出名单是在操作会话，这两个才拉起。

## 切换：没在跑的会话，读过的就记着

不再拉起之后，切回一个会话时有两样东西每次都把整份历史重解析一遍：上下文读数，和最后一轮交付
（`delivery:get`）。5MB 的会话各 15–25ms，都压在主进程上。现在都按日志的 `seq` 记着：读数与名单
在 `sessions:contextBreakdown` 旁边（设置换了也重读），交付只记切出来的那一轮消息，文件现在能不能
撤销照旧每次现查。

| 切回已打开过的会话 | 改前（会话已被拉起） | 只去掉拉起 | 改后 |
| --- | --- | --- | --- |
| 主进程事件循环最长卡 | 4–8ms | 21–40ms | 3–9ms |
| 点下去到画出来 | 39–66ms | 38–58ms | 40–68ms |
| IPC 载荷 | 343–393KB | 14–50KB | 14–68KB |

首次打开：点下去到画出来 75–92ms（改前 66–92ms），主进程最长卡 23–29ms（改前 23–25ms）。
`sessions:transcript` 主进程 9–22ms、1.8–3.3MB，序列化与反序列化各 1.4–3.4ms，不是瓶颈。

## 收尾的两处：少解析一遍、少起几个 git

在上面的基础上又做了两处。机器负载在 7–9 之间，单次结果不可信，所以改前、改后两份构建交替各跑 3 轮
（每份首次打开 9 次、切回 18 次），比较中位数：

| | 改前 | 改后 |
| --- | --- | --- |
| 首次打开：上下文读数 `sessions:contextBreakdown` | 16–24ms | 6–14ms |
| 首次打开：主进程 CPU（2.5s 内） | 190ms | 170ms |
| 每次切换：`git:stat` | 51ms | 45ms |
| 切回：点下去到画出来 / 稳定 / 渲染进程 CPU | 54 / 124 / 240ms | 55 / 122 / 240ms |

- **同一份历史只解析一遍**（`electron/session/stored-readings.ts`）。首次点开时，上下文读数和本轮交付前后脚
  都要整份历史，原来各自 `store.load` 一次。现在 `seq` 不变时共用一次读取，5 秒后放掉。读数、子代理名单、
  每轮交付后来也合进同一份按会话的缓存：键是 `seq` 加设置和项目设置文件，最近用过的 32 个会话留下；子代理
  只留名单摘要，详情点开时再从日志读。
- **`git:stat` 从 5 个进程减到 2 个**。`status --branch` 的表头本身就说明了是不是仓库、在哪个分支、有没有
  第一个提交（`statusBranch`），不必另外再问 `rev-parse` 和 `symbolic-ref`。每起一个进程，主进程要同步卡
  1.5–3ms。切换时重读不能省：离开期间别的会话或终端可能改过文件，而递归监听整个工作区在 Linux 上代价很高。

切回时的渲染没有改。试过让内容没变的子代理名单和 `capabilities` 不再写 store，写入记录确认少了那两次
`set`，但交替 A/B 的端到端数字没有差别，所以没留。切回时剩下的大头，是把隐藏的会话页重新显示出来后
那一次整页布局（14–24ms），强制发生在第一个读尺寸的 layout effect 里。它和浏览器下一帧本来就要做的是
同一次布局，提前读并不额外花时间。要让它变小只能给转录行加 `content-visibility`，而这已经量过、定过
不加（见 [对话渲染](conversation-rendering.md) 与 [ADR-0019](../adr/0019-no-virtual-list-yet.md)）。

## 启动：Dock 图标挪到窗口出现之后

`app.dock.setIcon` 把 1024px 的图同步交给 Dock，在主进程（也是 UI 线程）上约 50ms，预先解码也不更快。
它原来排在 `createWindow` 之前，窗口每次启动都晚这么久；挪到 `createWindow` 紧后面没有用（导航仍在
它后面排队），现在挂在窗口 `show` 之后。

| 从进程启动算起（7 次中位数） | 改前 | 改后 |
| --- | --- | --- |
| 窗口出现 | 555ms | 517ms |
| React 挂载 | 482ms | 448ms |
| 会话列表画出（启动屏退场） | 1431ms | 1402ms |

主进程建窗前的其余开销：ESM 加载与编译约 80ms、`buildAppWindow` 约 50ms、托盘 8ms。启动屏退场前共
7 次 IPC、约 176KB（`sessions:list` 163KB，主进程 0.7ms）。

## 看到了但不改

- **启动屏的 900ms 下限**（`MIN_BOOT_MS`）。数据约 585ms 就齐了，会话列表到 1.4s 才出现，差的几乎
  全是这条下限。它是刻意的体验决定，要不要缩短归产品，不归性能。
- **打开时渲染进程 50–69ms 的长任务**：滚动容器读 `scrollHeight`、标题滚字读 `offsetWidth`、输入框量
  `scrollWidth` 都会触发强制布局，但同一次提交里只有第一个读真正付出整页布局的代价（见上一节）。整段在
  100ms 判据内（见[流畅度对照清单](smoothness-checklist.md)第 11 条）。
- **载荷大小**：`sessions:transcript` 几 MB、`plugins:list` 首次 317KB（带技能全文）。序列化都在几毫秒，
  省下的字节换不来可感知的时间。
- **启动后的异步请求**：`updates:check` 1.5–2s（走网络）、`system:openTargets` 283ms、
  `files:locate` 一次打开 9 次共 200–250ms。都不挡界面，也不占主进程的同步时间。
