# 会话之间的消息

在跑的会话之间可以互相发现、问对方要回答、告诉对方一件事。用的是模型，不是人：工具只给模型，界面上
没有给人发消息的入口。照的是 t3code 的线程工具（`t3_thread_send` / `t3_thread_wait`）。为什么这样
设计见 [ADR-0040](../adr/0040-session-messaging.md)。

## 谁和谁能通信

- **只认在跑的会话。** 在跑的是主进程 `session-hub.ts` 那张表里已经起来、没在退场、没在删的会话。
  没起来的历史会话看不见，也不会被叫醒。侧聊、子代理、CLI 都不参与。
- **目录要重叠。** 每个会话的目录 = cwd + 所在项目的全部源目录 + （cwd 是链出去的 git worktree
  时）主工作树。两个会话的目录里有一对相同、或一个包含另一个，就互相看得见。比较前一律过
  `pathKey`（软链、`/var` 与 `/private/var`、Windows 大小写），包含判断用 core 的 `withinOrIs`。
  代码在 `electron/peer-reach.ts`。
- **对方权限比自己宽，不能发。** `ask` < `auto` < `full`，取两边叠加了项目层之后的
  `settingsInEffect.permissionMode`。防的是一个要审批的会话被拒之后，请一个不审批的会话代劳。反过来
  可以：宽的请窄的做事，窄的那边每一步照样走自己的审批。代码在 `electron/peer-policy.ts` 的
  `broaderThan`。

## 地址

`名字 [ref]`：名字是会话标题（没有就用目录名），ref 是 id 的前六位。名字会变、会重名，ref 不变，
所以解析时 ref 优先；重名又没带 ref 时不猜，把候选列出来。代码在 `electron/peer-address.ts`。

## 模型手里的工具

按意图分，不靠参数区分：「要回答」和「告诉一声」在对方那边走的路完全不同，参数一选错，要么白等，
要么让对方为一句通知专门跑一轮。

| 工具 | 做什么 |
| --- | --- |
| `list_sessions` | 列出能联系的会话：地址、忙闲、权限模式、cwd |
| `ask_session({ to, message, timeout_seconds? })` | **请求**，发出去就地等回答：对方闲着就开一轮，忙着就排到它手上这件事之后，单独占一轮；带回那一轮最后那段话。问几个会话可以并行 |
| `notify_session({ to, message })` | **通知**，当场返回：从不为它开一轮。对方在跑就在两步之间读到，闲着就攒到它下一次开工时读到。没有回答 |
| `wait_for_session({ to, timeout_seconds? })` | 接着等被打断的那几次问；没有这样的信，就等它手上这一次 |

四件都标了 `sessionOnly`，子代理拿不到。由 `session-hub.ts` 通过 `extraTools` 注入每个会话，状态全
在路由器里（`electron/session-peers.ts`）。工具说明和每一种退回的报错写在 `electron/peer-tools.ts`，
报错都说清下一步怎么做。

## 一条消息怎么走

```
ask_session / notify_session ─▶ 路由器（electron/session-peers.ts）
          ├─ 解析地址、查目录重叠
          ├─ 问：对方（直接或转手）正等着自己，退回
          ├─ 对方权限比自己宽：退回
          ├─ 限速 / 去重 / 链长（electron/peer-policy.ts）
          └─ AgentSession.receive
               ├─ 请求 ─▶ SessionDeliveries 攒 400ms，按发件会话分成几条，不和后台结果并在一起
               │           ├─ 闲着：第一条开一轮，其余排在后面各开一轮
               │           └─ 忙着：排到这一轮之后，另开一次运行；同一个会话紧挨着排队的几封
               │              合成一条、只开一次，不同会话的各开一次（SessionInbox.next）
               └─ 通知 ─▶ 攒在会话里，从不开轮
                           ├─ 在跑：下一步之前读到（和人插话同一处，drainSteering）
                           └─ 闲着：下一次开轮时最先读到（context 钩子）

ask_session 发完就地等 / wait_for_session 接着等（electron/peer-runs.ts 记着每封请求进了哪一次）
          ├─ 那一次运行结束：带回它最后那段话、怎么收的场
          ├─ 对方在等它的人回答：当场返回，同一件只报一次
          ├─ 请求还没进对话就被停下：说请求丢了
          └─ 人对发件方开口 / 超时 / 本轮被停 / 对方关了 / 互相等
```

进对话的是一条 `synthetic` 的 user 消息，带 `peer` 字段（`core/src/types/message.ts`）。给模型读的
正文由 `core/src/runtime/agent-session/peer-letters.ts` 拼：开头一段说明这不是用户说的话、不构成授权；请求还说
做完把结果写在这一轮最后一条回复里，通知说不需要专门回复；每条消息套
`<session-message from="名字 [ref]" cwd="…">`。界面上画成一行
（`PeerLetterRow`），点开读全文、一下跳到发消息的会话。请求对收到的一方是一件新的事，开新的一轮；
通知总是某一轮的输入（交出去时就打上 `steered`），不画成一轮的开头（`grouping.ts` 的 `opensTurn`）。
几家攒着的通知并成一条。

请求不是人开口：不放开正在等的子代理，也不清技能限制（`fromPerson: false`）。通知在对方跑着时会放开
它正在等的子代理或别的会话，和人插话一样——不然它要等那件事等完才读得到。

**消息不替代审批。** 收件方因为一条消息去做的每一件事，照常走它自己的审批。

## 问和等

问就是发一封请求、就地等它的回答，一次调用。最初发和等是两件工具，模型常常发完不等、或者等的时候
已经忘了自己问过什么；而几乎每一次发请求都是为了拿回答。

请求等的是**处理我那封信的那一次运行**，不是对方下一次空闲。对方正忙着人交代的事、或同时有别的
会话找它时，下一次空闲之前它可能跑了好几次，最后一句回答的是别人（照 synara 的 `wait_for_threads`）。

**一次运行只回答一家。** 运行的最后一段话会原样交给等它的人，所以几家的信不能落进同一次运行：
不同会话的请求各占一轮（和 qwen-code 一样，一封一轮），同一个会话连着的几封才合并。通知不开轮，
落在哪一次里那一次都在做别的事，所以它没有回答，也不用等。

- 一次运行 = `agent_start` 到 `agent_end`。hub 把每个会话的事件都交给路由器（`observe`），
  `peer-runs.ts` 记下每封请求（带 `id`）的 `message_start` 落在哪一次：请求总是排着进来、闲着时
  落盘，算下一次。开轮之前就被停下的只有 `agent_end`，当作刚开就结束的一次，收场是 `aborted`。
- 问只等自己这一封。被打断（超时、卡在等人回答上、人开口、本轮被停）时信照样在对方那里，路由器按
  「发件方→收件方」记着还没拿到回答的（最多 8 封）；`wait_for_session` 一次等齐它们，隔着别人的
  一轮分开处理的几封各带回一段回答，按发出的顺序、说清对着哪封。拿到了就从账上划掉。
- 结果是那次运行最后一段 assistant 文本，每段最多 4,000 字；截掉的部分告诉模型「请对方写进文件」。
- 对方在等它的人审批或回答问题时当场返回，让发件方去告诉人；同一件只报一次，再等就等到它被答完。
- 请求还在 400ms 里攒着就被对方的人按了停：请求跟着丢掉，答「丢了」，不拿它上一句冒充答复。
- 没有没拿到回答的信就 `wait_for_session`：照 t3code，闲着立刻返回它最后那句，忙着就等手上这一次。
- 默认等 600 秒，最多 1,800 秒。到点只是不等了，对方照常干。
- **人对发件方开口就不再等**：插话只在两次请求之间才有人读，等待会把人说的话压到对方做完为止。
  工具经 `ctx.untilSpokenTo`（core 的 `DelegationWaits.until`，和 ADR-0029 等子代理是同一套）
  当场交回；渲染进程看到主会话在 `ask_session` / `wait_for_session` 上时，人说的话直接插进去而不是
  排队（`awaitingSession`）。别的会话的通知落进来也一样放手（core 的 `AgentSession.receive`）。
- 发件方这一轮被人停下，`ctx.signal` 让等待立刻返回。对方在等待中被卸载，答「已关闭」。
- 互相等：路由器记着谁在等谁（一个会话可以同时等好几个，按次数记），顺着走回到自己就直接退回。
  问在发出去之前就查：对方（直接或转手）正等着自己时不发——它得先等这边答，而这边在等它。报错让
  模型把问题写进这一轮的回复里，等着它的那一方读的就是这一段。

发件方要结果就自己等，所以运行时不需要再递「它闲了」的回执，收件方也不需要再发一条消息回来——
那样会多开一轮去读一件已经知道的事。

## 防失控

都是确定的判断，拦下来时的报错告诉模型下一步怎么做：

| 规则 | 值 | 报错让它做什么 |
| --- | --- | --- |
| 单条长度 | 20,000 字符 | 写进文件，发路径 |
| 链长 | 28 跳 | 停止转手，交回给人 |
| 同一会话在链中 | 10 次 | 同上 |
| 同一对之间重复正文 | 30 秒内 | 不再发 |
| 令牌桶（按发件→收件） | 容量 30，每秒补 0.5 | 合成一条，或先等对方做完 |
| 互相等 | 顺着「谁在等谁」走回自己 | 先把自己那部分做完；问的话，把问题写进这一轮的回复 |

链：每条消息带经手的会话 id。链记在运行上：收件方在处理这封信的那一次运行里（请求开的那一轮，或
通知落进去的那一轮）再发出去的，链往后接；同一次里进了几家的信，接最长的那条。人开的那一轮、人在这一次
里开口之后，发的是一条新链。

20,000 这个上限是先定的：一条消息全文进收件方的上下文，超过这个量就该写文件。有了真实用量之后用
`pnpm audit:sessions` 量一次再调。

## 没有做的

- 给人用的入口（输入框里 @ 一个会话附上地址、叫醒点过名的会话）：这是模型之间的协作，人要交代
  另一个会话做事，直接去那个会话说。
- 冲突自动检测（「两个会话改了同一个文件就通知」）：没有可靠的信号，t3code 也没有做。模型自己发现
  文件在底下被改了，可以 `list_sessions` 找到是谁、问它或告诉它。
- 侧聊不参与：它挂在主会话旁边，主会话在名单上就够了；它要协调，经 `dispatch_task`、`control_main`
  对着自己的主会话说。
- 跨进程（CLI、多实例）没有通路：桌面端是单实例，路由放在主进程就够了。
- 不兼容 Claude Code 的会话：它的 socket 协议没有公开，带版本号，随时会变。
- 叫醒没起来的会话：只认已经起来的会话。原会话被回收后 fork 联系不上它，这一条也不例外——
  替没打开的会话开一轮、花钱，要人自己去开。
