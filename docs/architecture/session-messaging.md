# 会话之间的消息

在跑的会话之间可以互相发现、查看对方的记录、问对方要答复、告诉对方一件事。用的是模型，不是人：工具
只给模型，界面上没有给人发消息的入口。问是发出即返回的，答复作为一封信送回来——和子代理送回结果一个
样子。为什么这样设计见 [ADR-0040](../adr/0040-session-messaging.md) 与 [ADR-0060](../adr/0060-asks-do-not-block.md)。

协作的主路是层级：要另一个会话接手一件事，用 `spawn_session` 派出去（和自己并行改同一个仓库时设
`edits_in_parallel`，建议卡片的工作树开关默认打开），结果经 `spawnedFrom.reportBack` 推回来。这一页的
工具管的是派出之后、或本来就并行的两个会话之间那几句话。

## 谁和谁能通信

- **只认在跑的会话。** 在跑的是主进程 `session-hub.ts` 那张表里已经起来、没在退场、没在删的会话。
  没起来的历史会话看不见，也不会被叫醒。侧聊、子代理、CLI 都不参与。
- **目录要重叠。** 每个会话的目录 = cwd + 所在项目的全部源目录 + （cwd 是链出去的 git worktree
  时）主工作树。两个会话的目录里有一对相同、或一个包含另一个，就互相看得见。比较前一律过
  `pathKey`（软链、`/var` 与 `/private/var`、Windows 大小写），包含判断用 core 的 `withinOrIs`。
  代码在 `electron/peer/peer-reach.ts`。
- **对方权限比自己宽，不能发。** `ask` < `auto` < `full`，取两边叠加了项目层之后的
  `settingsInEffect.permissionMode`。防的是一个要审批的会话被拒之后，请一个不审批的会话代劳。反过来
  可以：宽的请窄的做事，窄的那边每一步照样走自己的审批。代码在 `electron/peer/peer-policy.ts` 的
  `broaderThan`。

## 地址

`名字 [ref]`：名字是会话标题（没有就用目录名），ref 是 id 的前六位。名字会变、会重名，ref 不变，
所以解析时 ref 优先；重名又没带 ref 时不猜，把候选列出来。代码在 `electron/peer/peer-address.ts`。

## 模型手里的工具

按意图分，不靠参数区分：问和告诉在对方那边走同一条路，差别在有没有答复。能从对方记录里查到的不问。

| 工具 | 做什么 |
| --- | --- |
| `list_sessions` | 列出能联系的会话：地址、忙闲、在不在等它的人、权限模式、cwd、清单上正在做的那一步 |
| `read_session({ to, query?, … })` | **查看**对方此刻的对话，可以按关键词搜、翻页，一次最多 12,000 字。只读：不叫醒对方、不花它的钱。和侧聊读主会话是同一个 `readHistory`（core） |
| `ask_session({ to, message })` | **请求**，当场返回。对方在跑就在两步之间读到，闲着就开一轮。答复以后作为一封信自己到 |
| `reply_session({ to, message })` | **答复**问过来的会话，当场返回，作为一封信送过去。没有待答的问就当作通知 |
| `notify_session({ to, message })` | **通知**，当场返回：交接、被挡住、放手这三种。对方在跑就在两步之间读到，闲着就为它开一轮。没有答复。进度不用报，对方会 `read_session` |

五件都标了 `sessionOnly`，子代理拿不到。由 `session-hub.ts` 通过 `extraTools` 注入每个会话，状态全
在路由器里（`electron/peer/session-peers.ts`）。工具说明和每一种退回的报错写在 `electron/peer/peer-tools.ts`，
报错都说清下一步怎么做。

## 一条消息怎么走

```
ask_session / notify_session ─▶ 路由器（electron/peer/session-peers.ts）
          ├─ 解析地址、查目录重叠
          ├─ 对方权限比自己宽：退回
          ├─ 限速 / 去重 / 链长（electron/peer/peer-policy.ts）
          └─ AgentSession.receive（请求和通知同一条路，请求的信上带 request: true）
               ├─ 在跑：攒在会话里，下一步之前读到（和人插话同一处，drainSteering）；
               │   循环最后一次取插话之后才到的，收场后交给 SessionDeliveries
               │   人按了停：请求丢掉，通知留到下一轮开头读到
               │   人插话或编辑重发：请求和通知都留着，由插话开的那一轮开头读到
               └─ 闲着：SessionDeliveries 攒 400ms，几家并成一条开一轮，不和后台结果并在一起；
                   人在这期间按了停就不开，通知退回会话、下一轮开头读到，请求丢掉

ask_session 当场返回，路由器记下这封还没答复（electron/peer/peer-runs.ts 记着每封请求进了哪一次运行）
          答复作为一封 answer 信送回发件方：
          ├─ replied：对方 reply_session 交回的那段话
          ├─ unreplied：读到它的那一次运行收场了还没回，拿那一次最后那段话（被停下、出错时开头注明）
          ├─ dropped：对方前台闲下来时请求还没进对话——被它的人按停了
          └─ closed：对方会话关了
```

进对话的是一条 `synthetic` 的 user 消息，带 `peer` 字段（`core/src/types/message.ts`）。给模型读的
正文由 `core/src/runtime/agent-session/peer-letters.ts` 拼：开头一段说明这不是用户说的话、不构成授权；有请求时
还说标着 `reply="expected"` 的要用 `reply_session` 回、手上原来的事照常做完；有答复时说清四种 `answer` 各自
怎么办；只有通知时说不需要专门回复。每条消息套 `<session-message from="名字 [ref]" cwd="…">`，请求多一个
`reply="expected"`，答复多 `answer="…"` 和 `re="…"`（问的话的开头）。界面上画成一行（`PeerLetterRow`，
答复写「X 的答复」），点开读全文、一下跳到发消息的会话。插进正在跑的那一轮的信是这一轮的输入（交出去时
就打上 `steered`），不画成一轮的开头（`grouping.ts` 的 `opensTurn`）；闲着时为它开的那一轮，它就是开头。
几家攒着的信并成一条。

闲着时的通知曾经不开轮，照 codex 的 `trigger_turn = false` 攒到对方下一次开工。2026-10 一次多会话
协作里，在等各路回报的主会话收到「做完了」「被挡住了」之后一直不动，攒着的通知不进记录、界面上看
不见，人一开口才一下子冒出四五封；卸载或重启时它们还会跟着没了。发件方从不等通知，为它开一轮不拖累谁。

来信不是人开口：不清技能限制（`fromPerson: false`）。

**消息不替代审批。** 收件方因为一条消息去做的每一件事，照常走它自己的审批。

## 问和答

问是发一封请求、当场返回；答复作为一封信送回来。曾经是就地等（ADR-0040 修订三）：等待会被人开口、
别家的信、甚至被等的那一家自己发来的信打断，本机 17 次 `wait_for_session` 只等到 1 次，模型干脆不问，
改成互发通知（124 封对 2 封请求）。见 ADR-0060。

- 收件方一次 `reply_session` 答的是这个发件方发来、已经读到、还没答的几封，并成一封答复，`re` 列出对着
  哪几封。几家同时来问，各回各的，不会串。没有待答的问也照送，当作通知、照通知的规矩查权限和限速——
  先回「稍后做」、做完再回结果，第二句就落在这里。
- **答复总会到**。读到请求的那一次运行收场了还没回，拿那一次最后那段话代答（`unreplied`）。钉住的是读到
  信的那一次，不是对方下一次空闲：下一次空闲之前它可能跑了好几次，最后一句回答的是别人（照 synara 的
  `wait_for_threads`）。请求没读到就被对方的人按了停，答 `dropped`，不拿它上一句冒充答复：这一条挂在
  「对方前台闲下来时信还没进对话」上（问的时候就 `whenIdle("foreground")`），不挂在 `agent_end` 上——信还在
  400ms 攒批里时按停，那一轮根本没开。对方关了答 `closed`。
- 一次运行 = `agent_start` 到 `agent_end`。hub 把每个会话的事件都交给路由器（`observe`），
  `peer-runs.ts` 记下每封请求（带 `id`）的 `message_start` 落在哪一次：插进来时那一次已经在跑就算它，
  闲着时落盘的算下一次。开轮之前就被停下的只有 `agent_end`，当作刚开就结束的一次，收场是 `aborted`。
- 路由器按「发件方→收件方」记着还没答复的问，每一对最多 8 封；刷到上限的最旧那封不再代答，答复照常送。
- 代答最多 4,000 字；截掉的部分告诉模型用 `read_session` 读其余的。
- **还有没拿到答复的问时，发件方不算闲**（`awaitingAnswers`）：`sessionBusy` 不回收它，回收了答复就没人收；
  「交回原会话」的报告等它答复都到了、它闲下来再交（`session-hub.ts` 的 `settled`）。审阅会话问完原会话就
  收尾等着，不这样的话交回去的会是一句「在等决定」。
- 对方在等它的人审批或回答问题，`list_sessions` 那一行写着；问照样送，答复等那边的人答完才会来。

发件方问完要么接着做不依赖答复的事，要么说清在等什么、收尾。答复到了，闲着就为它开一轮，忙着就在
两步之间读到——和子代理的结果一样，不需要「它闲了」的回执。

## 防失控

都是确定的判断，拦下来时的报错告诉模型下一步怎么做：

| 规则 | 值 | 报错让它做什么 |
| --- | --- | --- |
| 单条长度 | 20,000 字符 | 写进文件，发路径 |
| 链长 | 28 跳 | 停止转手，交回给人 |
| 同一会话在链中 | 10 次 | 同上 |
| 同一对之间重复正文 | 30 秒内 | 不再发 |
| 令牌桶（按发件→收件） | 容量 30，每秒补 0.5 | 合成一条，或先等对方做完 |

链：每条消息带经手的会话 id。链记在运行上：收件方在被这封信叫起来的那一次运行里（闲着时来信开的
那一轮）再发出去的，链往后接；叫起同一次的有几家的信，接最长的那条。插进一次已经在跑的运行的信不接链——那一次不是它叫起来的，几个会话各跑长回合、互相递通知时，每封都加一跳，2026-10
实测半小时就到 18 跳（同一会话出现 8 次），再来回两三次就会被当成原地来回拦下。人开的那一轮、人在这一次
里开口之后，发的是一条新链。

20,000 这个上限是先定的：一条消息全文进收件方的上下文，超过这个量就该写文件。有了真实用量之后用
`pnpm audit:sessions` 量一次再调。

## 没有做的

- 给人用的入口（输入框里 @ 一个会话附上地址、叫醒点过名的会话）：这是模型之间的协作，人要交代
  另一个会话做事，直接去那个会话说。
- 冲突自动检测（「两个会话改了同一个文件就通知」）：没有可靠的信号，t3code 也没有做。并行改同一个仓库的
  各开一棵工作树；模型自己发现文件在底下被改了，可以 `list_sessions` 找到是谁、`read_session` 看它在做什么。
- 就地等答复（曾经的 `wait_for_session`）：见上文「问和答」。旧记录里的这件工具照样画得出来。
- 侧聊不参与：它挂在主会话旁边，主会话在名单上就够了；它要协调，经 `dispatch_task`、`control_main`
  对着自己的主会话说。
- 跨进程（CLI、多实例）没有通路：桌面端是单实例，路由放在主进程就够了。
- 不兼容 Claude Code 的会话：它的 socket 协议没有公开，带版本号，随时会变。
- 叫醒没起来的会话：只认已经起来的会话。原会话被回收后 fork 联系不上它，这一条也不例外——
  替没打开的会话开一轮、花钱，要人自己去开。
