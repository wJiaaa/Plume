# 会话之间的消息

在跑的会话之间可以互相发现、问对方要回答、告诉对方一件事。用的是模型，不是人：工具只给模型，界面上
没有给人发消息的入口。照的是 t3code 的线程工具（`t3_thread_send` / `t3_thread_wait`）。为什么这样
设计见 [ADR-0040](../adr/0040-session-messaging.md)。

## 谁和谁能通信

- **只认在跑的会话。** 在跑的是主进程 `session-hub.ts` 那张表里已经起来、没在退场、没在删的会话。
  没起来的历史会话看不见，也不会被叫醒。侧聊、子代理、CLI 都不参与。
- **目录要重叠。** 每个会话的目录 = cwd + 所在项目的全部源目录 + （cwd 是链出去的 git worktree
  时）主工作树。两个会话的目录里有一对相同、或一个包含另一个，就互相看得见。比较前一律过
  `pathKey`（软链、`/var` 与 `/private/var`、Windows 大小写），包含判断用 core 的 `withinOrIs`。
  代码在 `electron/peer/peer-reach.ts`。
- **对方权限比自己宽，不能发。** `ask` < `auto` < `full`，取两边叠加了项目层之后的
  `settingsInEffect.permissionMode`。防的是一个要审批的会话被拒之后，请一个不审批的会话代劳。反过来
  可以：宽的请窄的做事，窄的那边每一步照样走自己的审批。代码在 `electron/peer/peer-policy.ts` 的
  `broaderThan`。

## 地址

`名字 [ref]`：名字是会话标题（没有就用目录名），ref 是 id 的前六位。名字会变、会重名，ref 不变，
所以解析时 ref 优先；重名又没带 ref 时不猜，把候选列出来。代码在 `electron/peer/peer-address.ts`。

## 模型手里的工具

按意图分，不靠参数区分：问和告诉在对方那边走同一条路，差别在有没有人等回答。参数一选错，要么白等，
要么对方回了一句没人收的话。

| 工具 | 做什么 |
| --- | --- |
| `list_sessions` | 列出能联系的会话：地址、忙闲、权限模式、cwd |
| `ask_session({ to, message, timeout_seconds? })` | **请求**，发出去就地等回答：对方在跑就在两步之间读到，闲着就开一轮；带回它用 `reply_session` 交回的话，读到却没回就收场的，带回那一次最后那段话。问几个会话可以并行 |
| `reply_session({ to, message })` | **回答**问过来的会话，当场返回。它正等着就当场拿到，不在等了就当作一封通知读到，再等也拿得到 |
| `notify_session({ to, message })` | **通知**，当场返回。对方在跑就在两步之间读到，闲着就为它开一轮。没有回答 |
| `wait_for_session({ to, timeout_seconds? })` | 接着等被打断的那几次问；没有这样的信，就等它手上这一轮。只看前台，不等它放到后台的子代理 |

五件都标了 `sessionOnly`，子代理拿不到。由 `session-hub.ts` 通过 `extraTools` 注入每个会话，状态全
在路由器里（`electron/peer/session-peers.ts`）。工具说明和每一种退回的报错写在 `electron/peer/peer-tools.ts`，
报错都说清下一步怎么做。

## 一条消息怎么走

```
ask_session / notify_session ─▶ 路由器（electron/peer/session-peers.ts）
          ├─ 解析地址、查目录重叠
          ├─ 对方权限比自己宽：退回
          ├─ 限速 / 去重 / 链长（electron/peer/peer-policy.ts）
          └─ AgentSession.receive（请求和通知同一条路，请求的信上带 request: true）
               ├─ 在跑：攒在会话里，下一步之前读到（和人插话同一处，drainSteering），放开它正在进行的等待；
               │   循环最后一次取插话之后才到的，收场后交给 SessionDeliveries
               │   人按了停：请求丢掉，通知留到下一轮开头读到
               └─ 闲着：SessionDeliveries 攒 400ms，几家并成一条开一轮，不和后台结果并在一起；
                   人在这期间按了停就不开，通知退回会话、下一轮开头读到，请求丢掉

ask_session 发完就地等 / wait_for_session 接着等（electron/peer/peer-runs.ts 记着每封请求进了哪一次）
          ├─ 对方 reply_session：当场带回那段话
          ├─ 读到它的那一次运行结束了还没回：带回那一次最后那段话、怎么收的场（兜底）
          ├─ 对方在等它的人回答：当场返回，同一件只报一次
          ├─ 请求还没进对话就被停下：说请求丢了
          └─ 人对发件方开口 / 超时 / 本轮被停 / 对方关了 / 互相等
```

进对话的是一条 `synthetic` 的 user 消息，带 `peer` 字段（`core/src/types/message.ts`）。给模型读的
正文由 `core/src/runtime/agent-session/peer-letters.ts` 拼：开头一段说明这不是用户说的话、不构成授权；有请求时
还说标着 `reply="expected"` 的要用 `reply_session` 回、手上原来的事照常做完，只有通知时说不需要专门回复；
每条消息套 `<session-message from="名字 [ref]" cwd="…">`，请求多一个 `reply="expected"`。界面上画成一行
（`PeerLetterRow`），点开读全文、一下跳到发消息的会话。插进正在跑的那一轮的信是这一轮的输入（交出去时
就打上 `steered`），不画成一轮的开头（`grouping.ts` 的 `opensTurn`）；闲着时为它开的那一轮，它就是开头。
几家攒着的信并成一条。

闲着时的通知曾经不开轮，照 codex 的 `trigger_turn = false` 攒到对方下一次开工。2026-10 一次多会话
协作里，在等各路回报的主会话收到「做完了」「被挡住了」之后一直不动，攒着的通知不进记录、界面上看
不见，人一开口才一下子冒出四五封；卸载或重启时它们还会跟着没了。发件方从不等通知，为它开一轮不拖累谁。

来信不是人开口：不清技能限制（`fromPerson: false`）。来信（请求和通知）在对方跑着时会放开
它正在等的子代理或别的会话，和人插话一样——不然它要等那件事等完才读得到。放开时工具照实说是来了
通知还是人开口了（`SpokenWaits` 交回 `{ spokenTo }`）：混成「你的用户说话了」，模型会去回应一个没开口的人。

**消息不替代审批。** 收件方因为一条消息去做的每一件事，照常走它自己的审批。

## 问和等

问就是发一封请求、就地等它的回答，一次调用。最初发和等是两件工具，模型常常发完不等、或者等的时候
已经忘了自己问过什么；而几乎每一次发请求都是为了拿回答。

请求等的是**对方用 `reply_session` 交回的那段话**，不是对方这一轮收场。曾经请求排在对方手上这一轮
之后、单独占一轮，回答就是那一轮最后那段话；一轮可以跑二十分钟，问的却常是两步之内答得上来的事，
发件方等不到就改发通知（见 ADR-0040 修订三）。

- 收件方一次回复答的是这个发件方发来、已经读到、读到它的那一次还没收场的几封。几家同时来问，各回
  各的，不会串。
- 发件方正等着：当场拿到。已经不等了（超时、被打断）：回答记在账上，同时当作一封通知送过去，之后
  `wait_for_session` 当场拿到（审阅会话靠这个 `done` 放行改文件）。没有待答的信也照通知送，照通知
  的规矩查权限和限速——先回「稍后做」、做完再回结果，第二句就落在这里。
- **兜底**：读到请求的那一次运行收场了还没回，拿那一次最后那段话当回答，告诉发件方对方没回复。钉住
  的是读到信的那一次，不是对方下一次空闲：下一次空闲之前它可能跑了好几次，最后一句回答的是别人
  （照 synara 的 `wait_for_threads`）。
- 一次运行 = `agent_start` 到 `agent_end`。hub 把每个会话的事件都交给路由器（`observe`），
  `peer-runs.ts` 记下每封请求（带 `id`）的 `message_start` 落在哪一次：插进来时那一次已经在跑就算它，
  闲着时落盘的算下一次。开轮之前就被停下的只有 `agent_end`，当作刚开就结束的一次，收场是 `aborted`。
- 问只等自己这一封。被打断（超时、卡在等人回答上、人开口、本轮被停）时信照样在对方那里，路由器按
  「发件方→收件方」记着还没拿到回答的（最多 8 封）；`wait_for_session` 一次等齐它们，分几次回答的
  几封各带回一段，按发出的顺序、说清对着哪封。拿到了就从账上划掉。
- 每段回答最多 4,000 字；截掉的部分告诉模型「请对方写进文件」。
- 对方在等它的人审批或回答问题时当场返回，让发件方去告诉人；同一件只报一次，再等就等到它被答完。
- 请求还在 400ms 里攒着就被对方的人按了停：请求跟着丢掉，答「丢了」，不拿它上一句冒充答复。
- 没有没拿到回答的信就 `wait_for_session`：照 t3code，闲着立刻返回它最后那句，忙着就等手上这一次。
  忙闲只看前台（`AgentSession.idleInForeground`）：在跑、攒着待送、任务队列里排着的算忙，放到后台的
  子代理不算。曾经连子代理一起等，对方主线早已停下，等的一方挂到超时也拿不到一句话；现在当场返回，
  并告诉它对方的子代理回来后会自己再开一轮，要后续就请对方做完时通知。会话回收仍看完整的 `idle`。
- 默认等 600 秒，最多 1,800 秒。到点只是不等了，对方照常干。
- **人对发件方开口就不再等**：插话只在两次请求之间才有人读，等待会把人说的话压到对方做完为止。
  工具经 `ctx.untilSpokenTo`（core 的 `SpokenWaits.until`，`runtime/agent-session/spoken-waits.ts`）
  当场交回；渲染进程看到主会话在 `ask_session` / `wait_for_session` 上时，人说的话直接插进去而不是
  排队（`awaitingSession`）。别的会话的通知落进来也一样放手（core 的 `AgentSession.receive`）。
- 发件方这一轮被人停下，`ctx.signal` 让等待立刻返回。对方在等待中被卸载，答「已关闭」。
- 互相等：路由器记着谁在等谁（一个会话可以同时等好几个，按次数记），`wait_for_session` 顺着走回到
  自己就直接退回。问不拦：请求会放开对方正在进行的等待，对方答完再接着等。

发件方要结果就自己等，所以运行时不需要再递「它闲了」的回执。

## 防失控

都是确定的判断，拦下来时的报错告诉模型下一步怎么做：

| 规则 | 值 | 报错让它做什么 |
| --- | --- | --- |
| 单条长度 | 20,000 字符 | 写进文件，发路径 |
| 链长 | 28 跳 | 停止转手，交回给人 |
| 同一会话在链中 | 10 次 | 同上 |
| 同一对之间重复正文 | 30 秒内 | 不再发 |
| 令牌桶（按发件→收件） | 容量 30，每秒补 0.5 | 合成一条，或先等对方做完 |
| 互相等（只拦 `wait_for_session`） | 顺着「谁在等谁」走回自己 | 先把自己那部分做完 |

链：每条消息带经手的会话 id。链记在运行上：收件方在被这封信叫起来的那一次运行里（闲着时来信开的
那一轮）再发出去的，链往后接；叫起同一次的有几家的信，接最长的那条。插进一次已经在跑的运行的信不接链——那一次不是它叫起来的，几个会话各跑长回合、互相递通知时，每封都加一跳，2026-10
实测半小时就到 18 跳（同一会话出现 8 次），再来回两三次就会被当成原地来回拦下。人开的那一轮、人在这一次
里开口之后，发的是一条新链。

20,000 这个上限是先定的：一条消息全文进收件方的上下文，超过这个量就该写文件。有了真实用量之后用
`pnpm audit:sessions` 量一次再调。

## 没有做的

- 给人用的入口（输入框里 @ 一个会话附上地址、叫醒点过名的会话）：这是模型之间的协作，人要交代
  另一个会话做事，直接去那个会话说。
- 冲突自动检测（「两个会话改了同一个文件就通知」）：没有可靠的信号，t3code 也没有做。模型自己发现
  文件在底下被改了，可以 `list_sessions` 找到是谁、问它或告诉它。
- 侧聊不参与：它挂在主会话旁边，主会话在名单上就够了；它要协调，经 `dispatch_task`、`control_main`
  对着自己的主会话说。
- 跨进程（CLI、多实例）没有通路：桌面端是单实例，路由放在主进程就够了。
- 不兼容 Claude Code 的会话：它的 socket 协议没有公开，带版本号，随时会变。
- 叫醒没起来的会话：只认已经起来的会话。原会话被回收后 fork 联系不上它，这一条也不例外——
  替没打开的会话开一轮、花钱，要人自己去开。
