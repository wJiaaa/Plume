# ADR-0040：会话之间可以发消息、等对方做完，路由在主进程，照 t3code 的线程工具

- 状态：已采纳；2026-10-20 修订两次：一次运行只回答一家；工具按意图分成问、告诉、等，通知不再开轮。见文末
- 日期：2026-10-08
- 相关：[会话之间的消息](../architecture/session-messaging.md)；[ADR-0029](0029-parent-lets-go-when-spoken-to.md)（后台结果送回）；`packages/core/src/runtime/{peer-letters,session-deliveries,session}.ts`；`packages/desktop/electron/{session-peers,peer-policy,peer-reach,peer-address,peer-tools}.ts`

## 背景

几个会话并行干活很常见——每个 worktree 一个，或者一个改接口、一个改调用方。干完一个要接着另一个时，
只能人在两个对话之间来回复制粘贴。Claude Code 2.1.224 起有跨会话消息：会话互相发现、互发纯文本，
对方忙时在工具轮之间读到，闲时开一轮；它在进程之间用注册表、Unix socket、token 握手实现。
t3code 的编排层有一组线程工具：列出线程、发消息（自动/排队/插话/重开）、等对方这一轮跑完拿回结果。

## 决定

**照 t3code：发和等分开，结果靠拉，不靠推。** 三件工具：`list_sessions`、`send_message`、
`wait_for_session`。要结果的一方发完自己调等待，对方这一轮做完，它最后那条回复作为这次调用的返回值
回来。发件方那一轮从头到尾没断过。

**等的是收到那条消息的那一次运行，对方忙时默认排队。** 照 synara：等待钉住具体的那一次运行，
不取「下一次空闲时的最后一句」——对方同时在做别的事时那句回答的是别人。对方忙时消息排到它手上这件
事之后，`steer` 才插进去，插进去等于打断它。对方在等它的人回答时等待当场返回，不干等到超时。

**人对发件方开口，等待就放手。** 和 ADR-0029 等子代理同一个理由、同一套机制（`untilSpokenTo`）：
插话只在两次请求之间才有人读，一个十分钟的等待会把人说的话压十分钟。

**路由放在桌面端主进程。** 所有会话都在 `session-hub.ts` 的同一张表里，不需要 socket 与鉴权那一层。
只认在跑的会话，侧聊、子代理、CLI 不参与。

**能不能通信看目录是否重叠。** 跨项目可以，前提是两边的目录有交集：cwd、所在项目的全部源目录、
worktree 的主工作树。最后一条是因为 worktree 建在项目目录之外，不认它，并行 worktree 之间的交接就
做不了。

**对方权限比自己宽，不让发。** 照 t3code「目标的模式不能比调用方宽」。防的是要审批的会话被拒之后，
请一个不审批的会话代劳。

**投递复用 `SessionDeliveries`。** 消息和子代理结果、后台命令走同一条路：攒 400ms，忙着插话、闲着
开轮，`fromPerson: false`。

**消息不是用户意图。** 正文开头写明不构成授权；收件方因为消息去做的事照常走自己的审批。

**防失控只用确定的信号**：长度、链长、同一会话在链中的次数、重复正文、令牌桶，外加「互相等」这一种
能确定的死锁。不判断「两个会话是不是在互相推诿」，`repetition.ts` 记着这类猜测误伤过两次。

## 走过的弯路

第一版是推的：`send_message` 带 `notify_when_idle`，对方闲下来时运行时往发件方递一条回执；审批类别
不同的两边，消息先压在收件方门口等人放行；设置里有一个接收策略；人在输入框里 @ 过的、没在跑的会话，
发消息时叫醒它。用下来每一样都在给人添事：

- 回执让发件方为它再开一轮，人看到的是一件事被切成好几截、好几个页脚。为此又做了「回执并进上一轮」，
  界面先出现两行、结束时才合成一行，更怪。
- 「它闲了」不是人想知道的，人要的是做完的结果。
- 放行卡片、接收策略、@ 叫醒都是让人去管模型之间的协作。

改成拉之后这些全部删掉：没有回执、没有放行卡片、没有设置项、没有给人用的入口，界面上只剩收件方
对话里那一行「来自 X」。

## 没有做的

- **冲突自动检测。** 「两个会话改了同一个文件就通知对方」没有可靠的信号，t3code 也没有做。
- **侧聊。** 它的设计就是不碰工作区，要动手交给主会话。
- **跨进程。** CLI 是一次一个任务的非交互入口（ADR-0031），没有需求。
- **与 Claude Code 会话互通。** 对方的协议没有公开，带版本号；冒充它的 peer 还会绕开对方用户的接收设置。
- **新的缝。** 只有一种实现，用 `extraTools` 注入工具、在 hub 里持有路由器就够了。新增的只有
  `Tool.sessionOnly` 一个字段：定义里 `tools: "*"` 的子代理继承会话全部工具，而它不该拿到这三件。

## 修订（2026-10-20）：一次运行只回答一家，插话是通知

等待带回的是「收到那封信的那一次运行」最后那段话。这条规则本身没错，错在几封信可以落进同一次运行，
而那段话原样交给每一个等它的人：

- 对方忙时，A、C 两家挨着排队的信被 `SessionInbox.next` 合成一条、只开一轮；400ms 内先后到的也合成
  一条，插话的还会并进子代理结果的送达。两家等回来的是同一段话，一半在回答别人，后半截还可能被
  4,000 字截掉。
- `steer` 的信算进对方正在跑的那一次，那一次多半在做人交代的事。发件方等到的是那件事的收尾，和自己
  的信无关。
- 路由器的往来链按收件方只记最近一封（后到的盖掉先到的，B 回 A 的信接在 C 的链上）；「谁在等谁」
  每个会话一个槽位，同一批里并发的两次 `wait_for_session` 互相覆盖，死等检测漏边；每一对只记最近
  一封信，连发两封的第一封等不到。

对照了两家（读源码）：qwen-code 会话之间的信一封一轮、从不插进正在跑的那一轮，回信要对方主动再发；
codex 把积压的信全部合成一轮，但结果只自动交给父代理，其余发件方什么也拿不到——两家都没有「几家
共用一段回答」。

改成：

1. **不同会话的信各占一轮。** 送达按发件会话分组，各成一条；同一个会话紧挨着排队的几封才合并。来信
   不再并进后台结果的送达。代价是几家同时来信时多几次请求，后一轮的前缀和前一轮几乎相同，缓存接得上。
2. **请求和通知。** 默认的 `queue` 是请求，等待带回处理它的那一轮最后那段话。`steer` 是通知：插进别人
   那一次的，读到就返回「已读到」；送到时对方闲着、自己开了一轮的，按请求等回答（以 `message_start`
   时那一次是否已经在跑为准，`peer-runs.ts`）。两种信的开头说明分开写，通知说不需要专门回复。
3. **账跟着信和运行走。** 往来链记在运行上；「谁在等谁」一对多、按次数记；路由器按「发件方→收件方」
   记着还没等过的信，一次等待等齐，各带回自己那一轮的回答。
4. **攒着的信不随会话回收。** `sessionBusy` 看 `AgentSession.idle`：信到了还在 400ms 里攒着时
   `running` 还是假，之前回收在这个空档里会把信一起扔掉。

没有改的：发和等仍然分开、结果仍然靠拉；不叫醒没起来的会话；侧聊、子代理不参与。

## 修订二（2026-10-20）：按意图分成问、告诉、等，通知不开轮

上一版之后还剩三处要靠模型「用对」：

- 发和等是两件工具。几乎每一次发请求都是为了拿回答，模型却常常发完不等，或者隔了几步才等，那时已经
  说不清自己问过什么——等回来的回答里要专门注明「这段对着你哪封信」。
- 请求和通知靠 `mode` 参数区分，而两者在对方那边走的路完全不同。选错了，要么白等一段不存在的回答，
  要么让对方为一句不需要回答的话开一轮。
- `steer` 送到时对方闲着，就自己开了一轮。一句「我要改 config.ts」让对方花一整轮，发件方还得等它跑完。
- 两边互相问会卡死：A 正等着 B 回答，B 反过来问 A，信排在 A 这一轮之后，而 A 这一轮在等 B。等待里
  的死等检测只在 `wait_for_session` 时才拦，那时信已经发出去了。

改成（通知这一条照 codex 的 `trigger_turn = false`）：

1. **`ask_session` = 发请求并就地等它的回答**，一次调用，问几个会话可以并行。被打断（人开口、超时、
   对方在等它的人、本轮被停）时信照样在对方那里，记在账上，`wait_for_session` 接着等。
2. **`notify_session` 从不开轮。** 对方在跑就在下一步之前读到，闲着就攒到它下一次开工时最先读到。
   不让对方变忙，没有回答，当场返回。
3. **`wait_for_session` 只剩两个用处**：接着等被打断的问，或者等对方把手上的事做完。
4. **问之前查「对方是不是正等着我」**，顺着「谁在等谁」走，直接或转手都算。是就不发，告诉模型把问题
   写进这一轮的回复——等着它的那一方读的就是这一段。

删掉了 `send_message`、它的 `mode` 参数、通知的「已读到」回执，以及 `peer-runs.ts` 里「这封是不是插进
去的」那一位：请求总是自己开一轮，通知不进账。

## 修订三（2026-10-28）：请求在两步之间送达，回答用 `reply_session` 交回

请求一直排在对方手上这一轮之后，单独占一轮，回答就是那一轮最后那段话。这条规则的前提是「一轮不会太
长」，实际不成立：2026-10-28 一次两个会话协作，收件方那一轮跑了 21 分钟、64 步还没收场，而一步的
间隔中位数 8.3 秒、90% 在 43 秒内、最长 157 秒（一条 mvn）。发件方问的是「你在改哪些文件」——两步
之内就答得上来——却 120 秒超时，只好改用通知；两边后来的协作全靠互发通知完成，问这条路形同虚设。
本机所有会话里 `ask_session` 一共 4 次，2 次超时（样本太少，只说明「等一轮」常常等不到，不当统计）。
截图上那条请求挂着「等这一轮结束」，人看不出它什么时候才会被读到。

「排在这一轮之后」只是为了拿到一个干净的边界：这一轮最后那段话只回答这一家。把回答和轮次脱钩，
这个边界就不再需要：

1. **请求和通知走同一条路。** 对方在跑就在下一步之前读到（`AgentSession.receive` → 和插话同一处
   `drainSteering`），闲着就开一轮；几家的信并成一条。请求在信上带 `request: true`，进对话时标签带
   `reply="expected"`，开头说明写清用 `reply_session` 回、手上原来的事照常做完。
2. **新增 `reply_session`。** 收件方把回答交回给发件方；这个发件方发来、已经读到、读到它的那一次还没
   收场的几封一起答。发件方正等着就当场拿到；已经不等了（超时、被人打断），回答照样记在账上，同时当作
   一封通知送过去——不记的话，之后 `wait_for_session` 拿不到 `done`，审阅会话靠它放行改文件的那一步就
   卡住了。没有待答的信也照通知送（照通知的规矩查权限和限速）：先回一句「稍后做」、做完再回结果，
   第二句就落在这里。
3. **兜底。** 读到请求的那一次运行收场了还没回，照旧拿那一次最后那段话当回答，并告诉发件方对方没有
   回复。模型忘了回，等的一方也不会挂到超时。
4. **对方正等着自己时照样能问。** 请求像人开口一样放开对方正在进行的等待（`SpokenWaits`），对方答完
   再接着等，不再互相死等，「问之前查对方是不是正等着我」那道拦截删掉。`wait_for_session` 的死等检测
   保留：两边都在等对方的回答、又都不再读新信时，仍然会卡住。
5. **人按停时**，没读到的请求跟着丢（发件方在等，路由器告诉它信没被读），通知照旧留到下一轮。

删掉的：`SessionInbox` 里按发件会话合并排队请求的逻辑、`SessionDeliveries` 的分组。输入框上方那一行
（`QueuedLetter`，由 `peer_queue` 事件驱动）样子不变，改成只在请求到了、对方还没读到的那一步之内出现，
右侧写「下一步读到」，不再是「等这一轮结束」。

代价：请求插进对方手上的事中间，可能把它带偏。通知早就这样插了，没见过因此跑偏；说明里写明先简短回答、
大活等手上的做完。往来链规则不变：插进一次已经在跑的运行的信不接链，请求现在也一样。
