# ADR-0057：一轮停了不等于做完了，同一个文件只有一个写入方

- 状态：已采纳
- 日期：2026-10-23
- 相关：core `agent/events.ts`（`TurnEnd`、`QueuedTask.unfinished`）、`runtime/agent-session/session.ts`（`prompt`、`submit`）、
  `runtime/queue/task-queue.ts`（`settledAs`）、`runtime/agent-session/delivery-message.ts`、`runtime/sub-agent/sub-agent-prompt.ts`（`workingNote`）、
  `runtime/sub-agent/sub-agents.ts`（`lookupResumable`）、`runtime/sub-agent/detached-dispatches.ts`、`tools/task.ts`；desktop
  `electron/session/scheduler.ts`、`electron/session/session-report-back.ts`、`src/features/sidechat/TaskStrip.tsx`

## 背景

拿「主智能体、子智能体、运行时怎么配合」的四条原则对照了一遍现状：运行结束、报告送达、用户目标完成是三件事；
相关的后续工作复用已有的子代理；同一份历史串行推进、互不依赖的有界并发；并行优先用于只读工作，写入归属明确。
大部分已经成立（ADR-0024 续跑、0029 并发闸门、0040 会话间消息、0051 一个一份送达），剩下几处：

| 缺口 | 现象 |
| --- | --- |
| 任务队列、定时任务只看 `prompt()` 抛没抛 | 服务商出错、原地打转、跑满轮数都是正常返回，任务条打勾、定时卡片上什么问题都没有 |
| 定时任务的防重入在会话建好时就放开 | 这一轮不被等待，间隔比一轮短的任务一次叠一次，同一个目录上好几个会话同时在改 |
| 子代理没做完的报告在标签上写 `status="done"` | 只有正文第一行的 ⚠ 说它没做完 |
| 子代理的交接不要求说验证到哪一步 | 派发说明让子代理跳过构建和测试、由父会话统一验证，父会话却不知道哪些没人核对过 |
| 对还在跑的子代理 `resume`，拒绝语是「不需要续跑」 | 手上真有后续那件事的模型，要么把它丢了，要么另派一个从零做 |
| 「交回这里」在第一次 `agent_end` 就交 | 派了子代理的会话交回的是「已派出」那句话，结论送不回来 |
| `task` 鼓励并行派、派完「接着做」 | 能写的几个子代理、以及父会话自己，可能同时改同一个文件 |

## 决定

1. **`prompt()` 交回它开的那一轮怎么收的场**（`TurnEnd`：`agent_end` 的 `reason` 与 `error`）。在排在它后面的那几轮之前
   取，并进别人那一轮的没有。改在这里，因为任务队列和定时任务都经过它；命令行本来就读 `agent_end`、等 `whenIdle`。
2. **任务队列**：出错、打转、跑满记成 `failed`——失败那一行本来就带「重试」。没有错误原文可转述的两种标在
   `unfinished` 上，由界面说是哪一种（ADR-0028）。不加新状态。
3. **定时任务**：同样三种写进 `lastError`、发失败通知；人按停的不算失败。这一次运行收尾（含后台子代理送回来的
   那几轮，`whenIdle`）之前，到期的 tick 跳过；`lastRunAt` 记的是开跑时间，所以收尾后只补跑一次。
4. **交接如实**：没做完的报告标签上带 `incomplete="true"`；子代理的工作说明要求列出改了哪些文件、跑过什么验证、
   没验证的明说，事实和推断分开。
5. **续跑被拒时说清下一步**：等结果送到之后再用 `resume` 交代下一件事，不要另派。
6. **「交回这里」等那件事做完再送。** 从建议开出来的会话，第一次 `agent_end` 之后还要等它闲下来（`whenIdle`），
   送最后那一轮的话、按最后那一轮的收场算。从前在第一次 `agent_end` 就送：派了子代理的那一轮当场收尾，送回去的是
   「已派出，等结果」，真正的结论送不回来——内置的 `/review` 默认派三个审查子代理，每次都撞上。交不交、撕条子
   仍在第一次 `agent_end` 当场定下：挪到闲下来之后，那段时间里退出应用，重启后条子还在，人后来的聊天会被交回去。
7. **同一个文件只有一个写入方。** `task` 的说明：可能改文件的子代理，在各自的 prompt 里写明负责哪些文件，两个不
   拿同一个文件；它在改的那些，父会话不动。派出之后那句「已派出」也说一遍。这是协作约定，不是锁。

## 没有做的

每一条都写着什么时候再做：

- **独立的验收状态、确认工具**：主 agent 按风险核对关键结论，靠的是派发说明与送达消息里的那几句话。要等出现
  「根据验收结果自动放行下一步」的流程。
- **每个子代理的后续任务队列**：结束之后显式 `resume` 已经够用。要等出现连续交办的实际需要。
- **写锁、自动合并、调度器**：同一个文件一个写入方是约定。要等量到并行写入确实互相覆盖、约定压不住。
- **只读角色的运行时强制**：`explore`、`review`、`verify` 带 `bash`，只读靠提示词和会话自己的审批。真要保证，
  限制得覆盖 shell 与 MCP，只拿掉写文件的工具不算数。
- **持久化的结果回执与消费确认**：跨进程恢复仍靠记下的事实（ADR-0033）、留下的上下文（ADR-0024）和重开后
  的说明（ADR-0051 第 6 条）。要等出现必须跨进程可靠交付的需求；在那之前，确认不了的执行结果不重跑、不标成功。
- **排队中的子代理在「已派出」那句里被说成「在后台跑」**：界面上已经标了排队，这句话对模型的行为没有影响。

## 后果

- 任务条上没做完的那种显示「没做完 · …… · 可重试」，定时卡片显示原因；`QueuedTask` 多了 `unfinished`。
- 定时任务不再叠跑：一轮比间隔长时，到期的那几次合成收尾后的一次。
- `task` 的说明、子代理的工作说明各多一句：每个会话的工具表、每个子代理的系统提示词的前缀变一次，之后照常命中缓存。
